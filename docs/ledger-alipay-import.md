# 支付宝详情截图导入

## 与旧 App 对齐的字段

参考原生 App 的 `ReceiptParser.swift` 中 `parseAlipayDetail`、
`extractAlipayDetailTitle`、`buildAlipayDetailItems`，以及
`LedgerModels.swift` 中的 `TransactionDraft.init(parsed:)`。

| 页面内容 | 填充规则 |
| --- | --- |
| 顶部商家名 | 优先作为流水名称，避免被“收钱码收款”等通用商品说明替代 |
| 顶部带正负号的金额 | 实际收支金额；不得优先采用订单原价 |
| 收款方全称、商户全称 | 保留为商户信息；缺失时使用顶部商家名 |
| 订单金额、原价 | 原价字段，与实际收支金额分开 |
| 支付遇财神、红包、立减等 | 识别优惠明细；没有明确优惠时，可以由原价与实付的差额补全 |
| 支付时间 | 订单日期与时间，编辑时保留秒数 |
| 付款方式 | 支付渠道；乱码或无法确认的文字保留在明细中，标为待核对 |
| 支付时间、付款方式、扣款说明 | 展示在编辑区的补充信息中 |
| 商品说明、优惠说明 | 追加到补充信息供用户对照 |
| 积分、领取奖励、服务推荐广告 | 不参与金额、优惠计算 |

和原生 App 一样，识别明细与用户备注分开。备注可以编辑，确认入账时保留。
导入前的识别过程不会直接写入流水。

## 识别过程

1. 在浏览器本地读取原图和增强图，分别解析候选结果。
2. 针对支付宝详情，利用文字坐标重新裁取顶部区域识别大号实付金额。
3. 在相同顶部金额下比较两份结果，优先保留原价、优惠等信息完整的结果。
4. 无法可靠识别的支付渠道留空，并提示对照原件补全，不猜测具体渠道。
5. 手机端直接显示补充信息，不再随侧栏一起隐藏。

图片由浏览器本地 OCR 处理。这次改动没有增加外部识别服务、密钥或数据库迁移。
该逻辑仅针对支付宝详情；其他平台继续使用原有解析分支。

## 移动浏览器补充处理

- 标题漏识别时，结合付款方式、商品说明、支付时间等字段识别支付宝详情。
- 图片解码支持 ImageBitmap 和 HTMLImageElement 两种路径，增强失败后仍执行顶部识别。
- 主金额只使用顶部收支金额或明确的实付字段；订单金额不再作为实付的备用值。
- 原价、优惠金额、溢价金额统一在补充信息区域编辑。

## 支付渠道补充识别

整页识别无法确认付款方式时，按文字坐标裁取该字段的值，去除左侧字段标签
与右侧箭头，单独用中文模型读取。普通字号保留原始像素，避免过度放大使短词
变形。此过程仍在浏览器本地执行，不会上传支付截图。

只有读到明确渠道名称、且置信度达到门槛时才回填；无法确认时仍提示待核对。
繁体名称（例如“花唄”）统一为简体渠道名称，银行名称和卡号尾号则完整保留。
新增模型约 1.65 MB，只在需要补充识别时加载，后续由浏览器缓存。
主识别任务释放后再启动补充识别，避免两个识别任务同时占用内存。

## 微信深色账单及截图回归

- 微信转账详情使用独立布局解析：名称来自顶部，收款方备注和服务菜单不能替代名称。
- 微信大号金额按文字坐标单独裁取，深色背景转为浅底后，用数字识别再次核对；不会将转账单号作为金额。
- 支付时间标签出现轻微 OCR 错误时，只有相邻值满足日期形态才纠正；付款方式标签的纠正要求值能匹配明确渠道。
- 银行名称、卡号尾号保留；银行字段内的“储著卡”纠正为“储蓄卡”。
- 原图、识别结果和预期值保留在本机私有目录，Git 中仅提交合成文本的回归用例。

2026-11-04 针对用户提供的 7 张截图实际执行浏览器 OCR 回归：
正常解码 7/7、ImageBitmap 不可用路径 7/7，共 96 项关键字段检查通过。
范围包括名称、实付、方向、订单时间、支付渠道、候选数量，以及适用订单的原价、优惠和企业餐抵扣。
完整记账单元测试为 183 项通过。此结果针对提供的样本集，不代表任意图片都能无误识别。

## 手机与桌面结果一致性

已复现相同文件在 Chrome 与 WebKit 中因图片预处理差异而产生不同文字结果。
记账截图现统一使用 OCR 引擎解码得到的 PNG；增强、裁剪缩放使用明确的 CPU 双线性算法，
避免依赖各浏览器的 GPU 插值。原件预览仍保留用户上传的文件。

语言模型缓存按引擎和模型内容指纹划分命名空间，不再使用历史的全局默认缓存键。
单元测试会校验缓存版本包含当前三份模型的指纹，避免换模型后继续读到旧缓存。
迁移缓存不清除账号、账本或未同步的本地流水。

同一原件在任一识别遍次已确认企业工作餐时，最终候选保留公司补贴渠道及 100% 抵扣设置，
避免选择另一份字段更完整的普通候选时丢失场景。原图、增强图都没有企业餐证据时不增加补贴。

编辑识别结果的原件区域新增折叠的“识别诊断”，显示识别版本、模型命名空间、
原图 SHA-256、统一图像 SHA-256、尺寸及引擎版本；不含识别文字和账号密钥，不随流水同步。
可用于判断两台设备是否实际上传了相同字节的文件、是否仍使用旧版页面。

跨浏览器回归：Chrome 桌面、WebKit 移动模式、WebKit 禁用 ImageBitmap 并预置历史错误模型缓存，
三组均为 7/7，共 144 项关键字段检查通过。Chrome 与 WebKit 对 7 张原图产生相同的统一图像指纹和完整 OCR 文字。
完整单元测试为 189 项通过。移动模式运行在本机，并非用户实体 iPhone，实体设备仍需刷新后复查。
