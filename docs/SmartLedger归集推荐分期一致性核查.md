## 一、流水归集

### 原版规则

原版 `Core/LedgerStore.swift`：

- `shouldAutoCollect`，1375 行：开关开启、日期范围匹配、收支/分类规则匹配。
- `matchesBookDateRange`，1925 行：使用本地自然日比较起止日期；没有任何日期边界时不匹配。
- `autoCollectCategoryIds` 空数组表示全部收支；`-1` 表示全部支出，`-2` 表示全部收入；普通分类包含其后代。
- `applyAutoCollectRules`，810 行：可移除当前账本不再符合规则的关联，也可补充归集所有匹配流水；保留其他账本关联。
- 注意：参数虽然命名为 `collectUnassignedNow`，实际会收集所有尚未关联到目标账本的匹配流水，包括已经关联其他账本的流水。

原版 `Views/BooksView.swift`：

- 628 行：启用归集先检查账本期间；665 行提供“今天作为开始日期”。
- 669 行：分别提供“保留已归集到本账本的流水”和“归集全部匹配流水”。
- 738 行：保存新规则并按用户选择执行历史流水处理。

### 网页版差异

位置：[ledger.ts](../smartledger/frontend/src/ledger.ts) 的 `assignAutoBooks`、[LedgerWorkspace.vue](../smartledger/frontend/src/LedgerWorkspace.vue) 的 `openEntry`、`saveEntry`、`createOrUpdateBook`、`transactionMatchesBook`。

1. **未设置期间也能开启并匹配所有日期**，与原版前置条件不同。
2. **日期取 ISO 字符串前十位**，没有转成本地自然日。例如香港时间 10 月 22 日 00:30 保存为 `2026-10-21T16:30:00Z`，会被错误排除在 10 月 22 日开始的账本外。
3. **没有全部支出、全部收入规则**。函数甚至不接收 `kind`，界面只能选择分类或全部分类。
4. **启用归集和导入历史被绑在一起**。拒绝“是否同时将历史流水加入”的确认后，代码把 `autoCollectEnabled` 设为 false，连未来归集也关闭。
5. **已经启用时修改期间或分类，不处理历史流水**。批量关联仅在 false → true 的首次开启路径执行；没有保留/移除旧关联的选择。
6. **默认开启推荐时，手动记账可能漏归集**。打开编辑器时分类为 null，分类限定的账本没有预选；后来选中分类，保存仍把空数组作为明确账本选择传入，不重新计算。
7. **关闭推荐且已手选其他账本时，不追加自动归集账本**。原版会合并两者。
8. **OCR 无法明确表达“不绑定账本”**。编辑时取消所有账本后，空数组又会在保存时变回自动归集或当前账本；原版有独立 `hasExplicitBookSelection` 标志。

## 二、账本推荐

### 原版行为

`LedgerStore.recommendedBooks`，1357 行：

1. 按流水日期筛选处于期间内的账本；推荐候选本身不受分类、自动归集开关限制。
2. 自动归集开启的账本优先。
3. 期间较短的账本优先。
4. 同条件按原版数值 ID 倒序。

`Views/CreateTransactionView.swift`，36、208 行：

- 推荐列表排除已经选中的账本。
- 新建显示“符合这些账本时间范围”，修改显示“可补充关联到这些账本”。
- 点击推荐项追加账本，保留其他选择；修改日期时由计算属性刷新推荐。
- 493 行：关闭推荐提示后，保存时追加符合自动归集条件的账本，即使已经手选其他账本。

### 网页版现状

- 存在 `bookAssignmentPromptEnabled` 设置项，但没有独立 `recommendedBooks` 计算和推荐列表。
- 手动编辑仍是原生 `multiple select`，提示按 Ctrl 多选；OCR 是所有账本的普通复选框。
- `openEntry` 的一次性自动预选不能覆盖原版推荐行为，也不随分类、日期重新计算。
- 只有开关和部分预选逻辑，不能算账本推荐完成。
- 网页版 ID 为 UUID，原版为整数；补齐同条件排序时，需要显式的创建时间/顺序字段或兼容映射，不能用 UUID 字典序代替“较新账本优先”。

## 三、分期

### 已有基础能力

`ledger.ts/createTransaction` 已生成分期组 ID、期号、总期数及原始总额；各期按月推进，月末取目标月份最后一天。本次验证总金额和组元数据保存正确。

### 与原版差异

| 项目 | 原版 | 网页版 |
| --- | --- | --- |
| 分期金额 | 每期先四舍五入到分，最后一期调平尾差 | 向下取整后，把余下的分依次放到前几期 |
| 100 元 / 3 期 | 33.33、33.33、33.34 | 33.34、33.33、33.33 |
| 起始月份 | 独立 `installmentStartMonth`，可与订单日期不同 | 没有字段和控件，始终从流水日期开始 |
| 修改普通流水为分期 | 替换为多期，保留首笔 ID 并维护关联 | 修改表单可以填月数，但保存仍是一笔，月数被旧值覆盖 |
| 编辑已有分期 | 明确告知不会重新拆分，提供专门操作 | 普通月数输入仍可改，但保存并不会调整期数 |
| 取消分期 | 合并该组流水、清空分期元数据，并迁移关联抵扣 | 未实现入口与业务函数 |
| 立即还清 | 汇总未到期流水为当前还清记录，删除未来记录，防止重复还清 | 未实现入口与业务函数 |
| 月数界面范围 | 手动 2–36，OCR 2–24 | 手动 1–120，OCR 2–120；核心未限制最大期数 |
| 创建分期同时报销 | 按原始总额和报销比例生成收入 | 只把首期传入报销函数，按首期金额计算 |

报销例子：100 元分 3 期，50% 报销，原版生成 50 元收入；网页生成 16.67 元收入。

原版证据：

- `Core/LedgerStore.swift`：219 行新建；286 行起始月份及分摊；345 行按原始总额创建抵扣；417 行普通流水转分期；919 行取消；986 行立即还清。
- `Views/CreateTransactionView.swift`：249 行已有分期操作；260 行月数范围。
- `Views/ImportReceiptView.swift`：944 行分期编辑及起始月份。
- `Models/LedgerModels.swift`：783 行明确账本选择标志；789 行分期开关、月数和起始月份草稿。

## 四、存储与同步结论

- **已验证**：现有账本规则、账本关联、分期组 ID、期号、期数、原始总额可完整写入并读回 IndexedDB。
- **源码确认**：网页版云同步、坚果云备份使用完整 JSON 快照；Java 接口用 `JsonNode` 接收快照，现有这些字段没有经过会主动丢弃它们的固定 DTO 映射。
- **尚未复现**：明确“未选择账本”的草稿状态、分期起始月份的生成/编辑流程、各个账本独立分账关联模型。当前每笔流水主要保存共享的 `bookIds` 和一套分账设置，不能视为与原版全部数据语义相同。
- `normalizeSnapshot` 对已有数组对象基本原样保留，因此不能简单断言未知字段一定丢失；但保留未知 JSON 不代表页面会识别或应用它。
- **未验证**：真实服务器与坚果云的上传、下载、跨设备冲突处理，以及 iOS 快照与网页快照格式互通。

## 六、建议修复顺序

1. 统一归集规则函数和本地日期判定，补齐收支规则、明确不绑定状态；让手动与 OCR 保存共用这套规则。

3. 实现独立推荐候选和排序、点击追加、多选与日期联动，按原版区分推荐和自动归集。
4. 先修分期尾差与关联报销金额，再补起始月份、普通流水转分期、取消合并和立即还清。
5. 对修改后的快照迁移、本地保存和真实云同步做集成验收；验证取消/还清后的抵扣关联和统计不重复。
